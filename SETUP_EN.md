## 1. How the system works

The system has **two source repositories** that produce context documents for Claude. Each has its own generation/editing mechanism, but both deliver to the same destination: the `zeclio-setup-claude` package published to Nexus.

```
┌─────────────────────────────────────┐     ┌──────────────────────────────────────────────┐
│   maxi-libs/web-components          │     │   ZEUS-Layout                                │
│                                     │     │                                              │
│  AUTO-GENERATED DOCS                │     │  MANUALLY MAINTAINED DOCS                    │
│  ───────────────────                │     │  ────────────────────────                    │
│  • mwc.md                           │     │  • login.md        (Keycloak auth, token$)   │
│    generated by npm run build       │     │  • root-config.md  (routes, import maps)     │
│    from the readme.md file of       │     │  • styleguide.md   (components, permissions) │
│    each Stencil component           │     │  • api.md          (HTTP, interceptors)      │
│                                     │     │  • state.md        (Redux in single-spa)     │
│  When to sync:                      │     │                                              │
│  → After editing a component        │     │  When to sync:                               │
│    and running npm run build        │     │  → After editing any of these .md files      │
│                                     │     │                                              │
│  Command:                           │     │  Command:                                    │
│  npm run sync:docs                  │     │  npm run sync:docs                           │
└──────────────────┬──────────────────┘     └─────────────────────┬────────────────────────┘
                   │                                              │
                   └─────────────────────┬────────────────────────┘
                                         │
                                         │  Both run the same script:
                                         │  scripts/sync-docs.js
                                         │  Reads .claude/docs/*.md → opens a PR on GitHub
                                         ▼
                         ┌─────────────────────────────────┐
                         │   maxi-adan/zeclio-setup-claude  │
                         │   (GitHub)                       │
                         │                                  │
                         │  PR created automatically        │
                         │  with the updated docs           │
                         │                                  │
                         │  On merge:                       │
                         │  → GitHub Action triggers        │
                         │  → Bumps patch version in        │
                         │    package.json                  │
                         │  → Publishes to Nexus            │
                         └──────────────────┬───────────────┘
                                            │
                                            ▼
                         ┌─────────────────────────────────┐
                         │   Nexus (npm registry)           │
                         │                                  │
                         │  New version available           │
                         │  zeclio-setup-claude@x.x.x       │
                         └──────────────────┬───────────────┘
                                            │
                                            ▼
                         ┌─────────────────────────────────┐
                         │   Microfrontend projects         │
                         │                                  │
                         │  npx zeclio-setup-claude         │
                         │                                  │
                         │  docs/*.md   → always            │
                         │               overwritten        │
                         │  other       → only if file      │
                         │  files         doesn't exist     │
                         └─────────────────────────────────┘
```

**One-sentence summary:** you edit a doc in its source repo → run `sync:docs` → a PR opens → someone merges it → the Action publishes a new version → projects run `npx zeclio-setup-claude` and receive the fresh docs.

## 2. Who does what

| Role | Tasks |
|---|---|
| **Admin** (once, ever) | Create the GitHub token, configure it as `GH_TOKEN` on their machine, configure the `NEXUS_TOKEN` secret in the repo |
| **Team member** (once per machine) | Install GitHub CLI (`gh`), configure `GH_TOKEN` in their shell profile |
| **Dev on `maxi-libs/web-components`** | Edit components → `npm run build` → `npm run sync:docs` when ready to publish updated docs |
| **Dev on `ZEUS-Layout`** | Edit `.md` files in `.claude/docs/` → `npm run sync:docs` when ready to publish updated docs |
| **Any dev** | Review and merge the PR in `zeclio-setup-claude`. Run `npx zeclio-setup-claude` in their projects to receive the latest docs. |

## 3. One-time setup — per machine

These steps are required **once per machine** from which you want to run `npm run sync:docs`.

### 3.1 Install GitHub CLI (`gh`)

The GitHub CLI is the tool the sync script uses to create PRs automatically.

**Windows:**

```powershell
winget install --id GitHub.cli
```

**Mac:**

```bash
brew install gh
```

After installing, **open a new terminal** so the PATH gets updated.

> If you use an IDE's built-in terminal (like Antigravity or VS Code integrated) that doesn't inherit the system PATH, the script handles this automatically. No extra steps needed.

---

### 3.2 Configure the GitHub token (`GH_TOKEN`)

The sync scripts use the `GH_TOKEN` environment variable to authenticate with GitHub. The `gh` CLI detects it automatically, so **you don't need to run `gh auth login`**.

#### Prior step — Admin generates the token (once, for the whole team)

1. Go to: `https://github.com/settings/personal-access-tokens/new`

2. Fill out the form with these values:

   | Field | Value |
   |---|---|
   | Token name | `zeclio-sync-docs` (or any name you prefer) |
   | Expiration | However long you need, e.g. `1 year` |
   | Resource owner | `maxi-adan` |

3. Under **Repository access**, select:
   - `Only select repositories`
   - Search for and select: `maxi-adan/zeclio-setup-claude`

4. Under **Permissions**, expand `Repository permissions` and configure:

   | Permission | Value |
   |---|---|
   | Contents | `Read and write` |
   | Pull requests | `Read and write` |

   Leave everything else as `No access`.

5. Click **Generate token** and copy the token (`github_pat_...`). **It is only shown once.**

6. Share the token with the team securely (not via chat — use a password manager, 1Password, or similar).

---

#### Save the token on your machine

Once you have the token, saving it takes one minute.

**Windows — PowerShell:**

```powershell
# 1. Add the token to your PowerShell profile (persists across sessions)
Add-Content $PROFILE "`n`$env:GH_TOKEN = 'github_pat_xxxx...'"

# 2. Reload the profile in the current session
. $PROFILE

# 3. Verify it works
gh api repos/maxi-adan/zeclio-setup-claude --jq ".name"
# Should respond: zeclio-setup-claude
```

**Mac — zsh (default since macOS Catalina):**

```bash
# 1. Add the token to your zsh profile (persists across sessions)
echo '\nexport GH_TOKEN="github_pat_xxxx..."' >> ~/.zshrc

# 2. Reload the profile in the current session
source ~/.zshrc

# 3. Verify it works
gh api repos/maxi-adan/zeclio-setup-claude --jq ".name"
# Should respond: zeclio-setup-claude
```

> If you use bash on Mac, replace `~/.zshrc` with `~/.bash_profile`.

---

### 3.3 Configure the `NEXUS_TOKEN` secret (admin only, once)

The GitHub Action needs this secret to publish the package to Nexus. It is configured once in the GitHub repository.

```
Go to: github.com/maxi-adan/zeclio-setup-claude
  → Settings
  → Secrets and variables
  → Actions
  → New repository secret
     Name:  NEXUS_TOKEN
     Value: (the _authToken from your Nexus .npmrc)
```

## 4. Daily workflow — `maxi-libs/web-components`

This workflow applies when you have edited one or more Stencil components (`ms-*`) and want the updated docs to reach all projects.

### Why `npm run build` is required first

`mwc.md` is **not written by hand** — it is auto-generated from the `readme.md` files that Stencil produces for each component during the build. If you skip the build and run `sync:docs` directly, the `mwc.md` that gets synced will be out of date.

### Steps

```powershell
# From maxi-libs/web-components/core/

# Step 1: Generate the updated doc
npm run build
# → Produces (among other things): .claude/docs/mwc.md

# Step 2: Sync all docs
npm run sync:docs
# → Uploads all .md files from .claude/docs/ to templates/docs/ in zeclio-setup-claude
# → Opens a PR automatically with the list of modified files
```

### What `sync:docs` does internally

1. Reads all `.md` files from `.claude/docs/`
2. For each file, uploads it to `templates/docs/` in the `maxi-adan/zeclio-setup-claude` repo via the GitHub API
3. If a new file appears that is not yet referenced in `templates/maxi-setup.md`, it automatically adds a row using the `description:` field from the file's frontmatter
4. Creates a PR with the title and list of files that changed

> For this to work, `GH_TOKEN` must be configured in your environment (see section 3.2).

## 5. Daily workflow — `ZEUS-Layout`

This workflow applies when you have edited one or more ZEUS platform docs and want the changes to reach all projects.

### What the ZEUS-Layout docs are

Unlike `mwc.md`, these docs are **written and maintained manually**. They live in `.claude/docs/` inside the `ZEUS-Layout` repo:

| File | What it documents |
|---|---|
| `login.md` | How to consume `@maxi/login`: `token$`, `validateToken`, `decodeJWT`, session patterns, usage rules |
| `root-config.md` | Microfrontend registration, active routes, import maps per environment, cross-app communication |
| `styleguide.md` | Full component catalog, form helpers, date utilities, permissions API, strict usage rules |
| `api.md` | HTTP service pattern: `instance.js` with interceptors, `validateToken`+`token$` for auth headers, `window.APP_CONFIG_*` for base URL, `logout()` on invalid token |
| `state.md` | Redux Toolkit in single-spa: isolated store per microfrontend, permissions slice, `usePermissions` hook, Provider setup, when to use Redux vs local state |

### Steps

```bash
# From ZEUS-Layout/

# Step 1: Edit the .md file(s) you need to update
# Example: editing .claude/docs/api.md to document a new endpoint

# Step 2: Sync
npm run sync:docs
# → Uploads all .md files from .claude/docs/ to templates/docs/ in zeclio-setup-claude
# → Opens a PR automatically with the list of modified files
```

**No prior `npm run build` needed** — the docs are ready to sync as soon as you edit them.

### Adding frontmatter to a new doc

If you create a doc that doesn't yet exist, add frontmatter at the top of the file so it appears correctly in the `maxi-setup.md` table:

```markdown
---
name: my-doc
description: When and how to use this module — this description appears in the maxi-setup.md table
---

# Rest of the content...
```

The sync script reads the `description:` and uses it when inserting the row in `maxi-setup.md` automatically.

## 6. What happens after the PR

Once you run `npm run sync:docs` from either repo:

### Step 1 — PR review

The PR opens at `github.com/maxi-adan/zeclio-setup-claude`. Any team member can review and merge it. Check that:
- The modified files are the expected ones
- The diff content makes sense (no broken lines, valid markdown)

### Step 2 — Automatic GitHub Action

On merge, the GitHub Action `.github/workflows/publish-on-merge.yml` triggers **automatically**. No manual steps needed. The Action:

1. Detects that the PR touched files inside `templates/`
2. Bumps the patch version in `package.json` (e.g. `1.4.2` → `1.4.3`)
3. Publishes the new version to Nexus using the `NEXUS_TOKEN` secret

> If the PR doesn't touch files in `templates/`, the Action won't trigger. Check the Actions tab in the repo if you don't see any activity.

## 7. How to update microfrontend projects

Once the new version is published to Nexus, any dev can update their project with a single command:

```powershell
# From the root of the microfrontend project
npx zeclio-setup-claude
```

**What this command does:**

| File | Behavior |
|---|---|
| Everything in `.claude/` (docs, skills, maxi-setup, settings) | **Always overwritten** — all platform-managed files |
| `.specify/extensions/git/scripts/*` | **Always overwritten** — platform scripts |
| `.specify/extensions/git/commands/*` | **Always overwritten** — platform commands |
| `.specify/extensions/git/extension.yml` | **Always overwritten** — platform config |
| `SETUP.md` at the root | Only copied if it doesn't exist yet — never overwritten |
| `.specify/memory/constitution.md` | Only copied if it doesn't exist yet — never overwritten |
| `.specify/extensions.yml`, `init-options.json`, `git-config.yml` | Only copied if they don't exist yet |
| `CLAUDE.md` | Blocks are injected if not already present (idempotent) |

> If you want to reset all files to their template values (not just docs), run:
> ```powershell
> npx zeclio-setup-claude --force
> ```
> **Use with care** — this also overwrites files the team may have customized.

## 8. Auto-update — how `.version` works

Every project that uses `zeclio-setup-claude` has a `.claude/.version` file that records which version of the package was used to initialize or update the `.claude/` structure. This file is the foundation of the auto-update mechanism.

### What happens when Claude opens the project

At the start of **every session**, before responding to any message, Claude automatically runs these steps (instructions defined in `.claude/maxi-setup.md`):

**Step 1 — Read the installed version**

```
.claude/.version  →  e.g. "1.4.2"
```

**Step 2 — Query the version available in Nexus**

```bash
npm view zeclio-setup-claude version \
  --registry=https://artifacts.maxilabs.net/repository/maxi-npm-group/
# Responds: "1.4.5"
```

**Step 3 — Act based on the result**

| Situation | What Claude does |
|---|---|
| `.claude/.version` **does not exist** | Runs `npx zeclio-setup-claude --force` without asking |
| Installed version **≠** version in Nexus | Runs `npx zeclio-setup-claude@latest --force` without asking |
| Versions **match** | Does nothing, continues normally |

> Claude doesn't notify you when it updates — it just does it and continues with your request. If you want to know what version is installed, you can read `.claude/.version` directly.

**Step 4 — Verify that `CLAUDE.md` is initialized**

Claude reads `CLAUDE.md`. If the file **has no `##` sections** with project-specific content (only the `@` directives and maintenance rules injected by the script), it asks once:

> "This project doesn't have architecture documentation in `CLAUDE.md` yet. Would you like me to run `/init` first? I'll analyze the project and document commands, architecture, and patterns — which improves the quality of my responses."

- If you say **yes** → Claude runs `/init`, documents the project, and resumes your original request.
- If you say **no** → continues normally, doesn't ask again that session.
- If `CLAUDE.md` already has sections → asks nothing.

### Why this mechanism exists

The docs in `.claude/docs/` (especially `mwc.md`) change every time a component is updated in `maxi-libs/web-components`. Without this mechanism, a project could be working with an outdated component reference for weeks without knowing it. The auto-update ensures Claude always has the most current documentation before touching any code.

## 9. What each doc is for

The files in `.claude/docs/` are the **platform context** Claude reads at the start of each session. Without them, Claude doesn't know you're in a ZEUS microfrontend, doesn't know the `ms-*` components, doesn't know how authentication works, and could generate code that looks correct but violates critical platform rules.

Each doc has a specific purpose:

---

### `login.md` — Authentication and session

**When Claude uses it:** any time the code touches authentication, tokens, user session, or route protection.

**What it contains:**

- How to import and consume `@maxi/login`
- The `token$` observable — how to subscribe and read the current token
- `validateToken()` — when to call it (before critical or long-running operations)
- `decodeJWT()` — how to decode the token payload to read claims
- Session patterns: how to know if the user is authenticated, how to react to expiration
- Rules for what NOT to do: never store the token in `localStorage`, never call `keycloak.init()` from a microfrontend

**Real-world example:**

> "How do I make a component only show for users with the `ADMIN` role?"
> → Claude reads `login.md` and `constitution.md` to answer with the correct pattern using `validatePermission()`.

---

### `mwc.md` — Maxi Web Components

**When Claude uses it:** any time the code uses or needs to use any `ms-*` or `Ms*` component.

**What it contains:**

- Full reference for all components: `MsTable`, `MsDialog`, `MsDropdown`, `MsInputField`, `MsCalendar`, `MsMultiselect`, `MsNotification`, `MsFileUpload`, etc.
- Exact props for each component (names don't follow HTML standards — they're non-obvious)
- Events: what they're called, how to listen to them in React (with `on` prefix)
- How to pass objects/arrays as props (always as JavaScript objects, never as JSON strings)
- **`⚠️ ZEUS Exceptions` section** at the top — mandatory rules specific to the single-spa + React 17 context:
  - `MsDialog`: never render with `visible=true` before data is ready
  - `MsDialog`: use `key={record.id}` when the same dialog shows different records
  - `MsTable`: always `size="small"`
  - `MsTable`: always `ms-table-actions` on clickable elements inside cells
  - `MsTable`: numeric columns always `align: 'right'`

> This is the doc that changes most frequently — it's auto-generated with every `npm run build` in `maxi-libs/web-components`. That's why docs are always overwritten by `npx zeclio-setup-claude`.

---

### `root-config.md` — Routes and import maps

**When Claude uses it:** when the code touches routes, microfrontend registration, application startup, or cross-app communication.

**What it contains:**

- How microfrontend registration works in single-spa
- Active routes: which path activates which microfrontend
- Import maps per environment (local, dev, staging, production)
- Startup sequence: in what order the modules start up
- Cross-app communication: how one microfrontend can talk to another
- How to add a new microfrontend to the system

---

### `styleguide.md` — UI components and utilities

**When Claude uses it:** when the code uses components from `@maxi/styleguide`, form helpers, date utilities, or permission controls.

**What it contains:**

- Full catalog of available styleguide components
- Form helpers: patterns for building forms with validation
- Date utilities: functions for formatting and parsing dates
- Permissions API: `validatePermission()`, `validateGroupPermissions()`, `getUserRoles()` — how to use each and when
- Strict rules: when each component can and cannot be used
- Rule #15: how to override CSS for `ms-*` components without breaking scope (using the `class` or `customClass` prop)

---

### `api.md` — HTTP pattern

**When Claude uses it:** any time the code makes HTTP calls to a backend.

**What it contains:**

- The `instance.js` pattern: how to create the axios/fetch instance with the correct interceptors
- How to add the authentication header automatically using `token$`
- `window.APP_CONFIG_*`: how to read the backend base URL from environment config (never hardcoded)
- What to do when the token is invalid: call `logout()` and redirect
- Complete pattern for an HTTP service in ZEUS: imports, instance, request interceptor, response interceptor

> Without this doc, Claude would generate HTTP calls without auth or with a hardcoded URL — common errors this doc explicitly prevents.

---

### `state.md` — Redux Toolkit in single-spa

**When Claude uses it:** when the code needs global state, user permissions in the store, or Provider setup.

**What it contains:**

- Why each microfrontend has its own isolated store (they don't share a store with other microfrontends)
- How to configure Redux Toolkit in a ZEUS microfrontend
- The `permissions slice`: how the user permission state is loaded and updated
- The `usePermissions()` hook: how to read permissions from any component
- `Provider` setup: where and how to wrap it correctly in single-spa
- When to use Redux vs local state (`useState`): simple rule — permissions and data shared across routes go in the store; local UI state goes in `useState`

---

### `.specify/memory/constitution.md` — ZEUS Principles

**When Claude uses it:** in every `/speckit-plan` and `/speckit-implement` task as a quality gate. Also available in any code task when the rules are relevant.

**What it contains:**

The non-negotiable principles of the ZEUS platform, organized in sections:

| Section | What it prohibits / requires |
|---|---|
| I. Shared modules | All UI comes from `@maxi/styleguide`. Never install `maxi-react-components` directly. |
| II. Authentication | Never re-implement auth. Use `token$` or `props.token` from `@maxi/login`. Never store token in storage. |
| III. Native HTML controls | Prohibited: `<input>`, `<select>`, `<table>`, `<dialog>`. Always use the `Ms*` equivalents. |
| IV. Permissions | Use `validatePermission()` from the styleguide. Never `user.role === 'admin'`. |
| V. Ms* props and events | Verify exact props in `mwc.md` before using any component. |
| VI. Dependencies | Never duplicate React, RxJS, single-spa — they're in the global import map. |
| VII. CSS and theme | Global CSS imported once. Never target internal component classes without scope. |

> If Claude detects a violation during `/speckit-plan` or `/speckit-implement`, it **reports the problem before continuing** — it doesn't silently skip it.

## 10. SpecKit

SpecKit is the structured workflow system for medium and large features. It converts a natural language description into: specification → technical design → task list → implemented code, with the constitution as a quality gate at each step.

It consists of a set of **slash commands** you type directly in the Claude Code chat.

### When to use it

| Situation | Use SpecKit? |
|---|---|
| New feature of medium or large complexity (more than 2-3 files) | **Yes** |
| Feature involving multiple components, services, or routes | **Yes** |
| Feature whose implementation isn't clear upfront | **Yes** |
| Change that affects contracts or integrations with other microfrontends | **Yes** |
| Simple bug fix | **No** — use the chat directly |
| Text, color, or style change | **No** — use the chat directly |
| Internal refactor of a single file | **No** — use the chat directly |
| Adding a field to an existing form | **No** — use the chat directly |
| Single-line code change | **No** — use the chat directly |

**Simple rule:** if you can tell Claude exactly what to change in the chat and it makes sense to do it there, do it there. SpecKit is worth it when the work requires thinking before coding.

---

### Full SpecKit workflow

The standard flow has 4 required steps and 1 optional:

```
/speckit-specify  →  /speckit-clarify (optional)  →  /speckit-plan  →  /speckit-tasks  →  /speckit-implement
```

Each command produces an artifact the next one uses as input. You can't skip steps — `/speckit-plan` needs the `spec.md` that `/speckit-specify` generates.

---

#### Step 1 — `/speckit-specify <feature description>`

**What it does:**
Converts your natural language description into a formal functional specification. Claude writes it to `specs/NNN-feature-name/spec.md`.

Before creating the branch, Claude asks **two mandatory questions in sequence**:

1. **Branch type:** `feat` (new feature) or `fix` (bug fix)
2. **Branch name:** shows a suggested name based on your description and waits for you to confirm or provide a different one

The branch is created as `feat/NNN-name` or `fix/NNN-name` based on your answers.

The spec is written for non-technical stakeholders — it describes **what** the feature does and **for whom**, without implementation details. Includes: actors, user scenarios, functional requirements, measurable success criteria.

**How you interact:**
You type the command followed by the description directly in the chat. Claude may ask up to 3 clarifying questions if there are critical ambiguities (no more than that — it makes reasonable assumptions for the rest).

```
/speckit-specify I want to add a reports module that allows filtering by 
date range and exporting to Excel. Users with AUDITOR role can see all 
reports; users with USER role can only see their own.
```

Claude responds with the complete spec and asks for confirmation if there are ambiguous points.

---

#### Step 2 (optional) — `/speckit-clarify`

**What it does:**
Analyzes the existing spec and identifies ambiguities that could cause rework in later stages. Asks up to 5 questions, one at a time, and updates the spec with each answer.

**When to use it:**
If the spec has sections marked `[NEEDS CLARIFICATION]`, or if you know there are important design decisions that weren't clear in the initial description.

**How you interact:**
```
/speckit-clarify
```
Claude asks questions one at a time, with answer options and a recommendation. You respond with the option letter or free text.

---

#### Step 3 — `/speckit-plan`

**What it does:**
Reads the spec and generates the complete technical design. Produces several artifacts in `specs/NNN-feature-name/`:

| Artifact | Content |
|---|---|
| `plan.md` | Tech stack, file structure, architecture, design decisions |
| `research.md` | Resolution of technical unknowns (Claude researches best practices) |
| `data-model.md` | Entities, relationships, validation rules |
| `contracts/` | Public interfaces of the feature (endpoints, props, events) |

**Constitution check:** before finalizing the plan, Claude verifies it doesn't violate any principle in `.specify/memory/constitution.md`. If there are violations, it reports them and doesn't continue.

**How you interact:**
```
/speckit-plan
```
Mostly automatic. Claude may ask for confirmation on high-impact architecture decisions (e.g., if a feature requires sharing state between microfrontends).

---

#### Step 4 — `/speckit-tasks`

**What it does:**
Converts the plan into an actionable task list in `specs/NNN-feature-name/tasks.md`. Each task has:
- Unique ID (`T001`, `T002`...)
- Parallelization marker `[P]` if it can run in parallel with others
- User story label `[US1]`, `[US2]`...
- Description with the **exact file path**

**How you interact:**
```
/speckit-tasks
```

## 11. Updating project templates

In addition to docs, `zeclio-setup-claude` distributes other files and logic that also need to stay up to date.

### `templates-root/SETUP.md` (this file)

The workflow guide that gets created at the root of each new project. To update it:

1. Edit `templates-root/SETUP.md` in the `maxi-adan/zeclio-setup-claude` repo directly.
2. The change reaches **new** projects on the next `npx zeclio-setup-claude`.
3. Existing projects **are not updated automatically** — `SETUP.md` is never overwritten. If the change is critical, notify the team to run `npx zeclio-setup-claude --force`.

### `templates-root/.specify/memory/constitution.md`

ZEUS principles that SpecKit uses as a quality gate in `/speckit-plan` and `/speckit-implement`. To update it:

1. Edit `templates-root/.specify/memory/constitution.md` in this repo.
2. Same behavior as `SETUP.md`: only reaches new projects or projects that run `--force`.

### `CLAUDE.md` injections

The two blocks injected into `CLAUDE.md` in each project are **hardcoded in `zeclio-setup-claude.js`**, not a template file. To add a new injection:

1. Edit the `if (!DRY_RUN)` block at the end of `main()` in `zeclio-setup-claude.js`.
2. Follow the existing pattern:
   - Define a **unique marker** (a string that identifies whether the block was already injected)
   - Define the **text to inject**
   - Check if the marker is already present before writing (idempotency)
3. These injections **run on every execution** (with or without `--force`) — idempotency is guaranteed by the marker.

## 12. Adding a new platform doc

Docs are created in the source repo according to their nature. The rule is simple:

| Doc type | Source repo | How it's generated |
|---|---|---|
| `ms-*` component docs | `maxi-libs/web-components` | Auto-generated by `npm run build` from Stencil component `readme.md` files |
| ZEUS platform docs (auth, routes, HTTP, state, etc.) | `ZEUS-Layout` | Written and maintained manually in `.claude/docs/` |

**Steps from either repo:**

1. Create the `.md` file in `.claude/docs/` inside the corresponding repo.

2. Add frontmatter with `description:` (required for the script to register it in `maxi-setup.md`):

   ```markdown
   ---
   name: my-doc
   description: When and how to use this module — appears in the maxi-setup.md table
   ---
   ```

3. Run `npm run sync:docs` — the script detects the new file, uploads it to `templates/docs/`, and opens a PR.

4. The script automatically adds the row to `maxi-setup.md` using the frontmatter `description:`.

5. Merge the PR → GitHub Action publishes new version → projects update with `npx zeclio-setup-claude`.

**Current docs and their source repo:**

| Doc | Source repo | Type |
|---|---|---|
| `mwc.md` | `maxi-libs/web-components` | Auto-generated |
| `login.md` | `ZEUS-Layout` | Manual |
| `root-config.md` | `ZEUS-Layout` | Manual |
| `styleguide.md` | `ZEUS-Layout` | Manual |
| `api.md` | `ZEUS-Layout` | Manual |
| `state.md` | `ZEUS-Layout` | Manual |

## 13. ZEUS exceptions in `mwc.md`

ZEUS exceptions are component behaviors that differ from the default when used in a **single-spa + React 17** context. They are documented in the `⚠️ ZEUS Exceptions` section at the top of `mwc.md`. They are **mandatory** across all microfrontends.

### Current rules

| Component | Rule | Why |
|---|---|---|
| `MsDialog` | Never render with `visible=true` before the data is ready. Pattern: `useState(false)` + `if (!visible) return null` + show only after the fetch resolves. | Prevents the dialog from opening empty and then "jumping" with content. |
| `MsDialog` | When the same dialog shows different records (row-by-row editing in a table), use `key={record.id}` to force a remount. | Without `key`, React reuses the instance and the content stays stale from the previous record. |
| `MsTable` | Columns with numeric values (money, quantities, percentages) always use `align: 'right'` and `alignHeader: 'right'`. | ZEUS visual standard — numbers are right-aligned. |
| `MsTable` | Always use `size="small"`. | The default `"normal"` produces rows that are too tall for ZEUS designs. |
| `MsTable` | Any clickable element inside a cell (`render`) **must** be wrapped in `<div class="ms-table-actions">`. | Without this class, the click propagates to the row and triggers `rowClick` or the expand toggle. This behavior is hardcoded in `ms-table.tsx`. |
| Global CSS | **Do not import** `global.css` or `global-zeclio.css` in any microfrontend. `@maxi/styleguide` already imports `global-zeclio.css` when the single-spa starts. | Double import can cause conflicts. All `--maxi-*` CSS variables are already available. For overrides, set CSS variables in the project's global stylesheet. |
| `MsSidebar` | The overlay (`ms-sidebar-overlay`) can throw a `removeChild` crash in race conditions with single-spa. **Workaround:** implement side panels as a native `<aside>` with `position:fixed`. Fix pending in the library. | Conditional rendering in Stencil + a click-outside event still propagating → Stencil calls `removeChild` on a node React has already removed. |

### How to add a new exception

1. Discover the unexpected behavior in a real microfrontend.
2. Document the rule in the `⚠️ ZEUS Exceptions` section of `.claude/docs/mwc.md` in `maxi-libs/web-components`.
3. Replicate the same rule in `templates/docs/mwc.md` in `zeclio-setup-claude` (this repo).
4. Run `npm run sync:docs` or edit `templates/docs/mwc.md` directly.
5. Merge the PR → the new version travels to all projects with `npx zeclio-setup-claude`.
6. Register the exception in the table in this section to keep this doc up to date.

## 15. Troubleshooting

| Problem | Likely cause | Solution |
|---|---|---|
| `gh: command not found` (Windows) | `gh` not installed or terminal didn't reload the PATH | Open a new terminal. If it persists: `winget install --id GitHub.cli` |
| `gh: command not found` (Mac) | Same as above | Open a new terminal. If it persists: `brew install gh` |
| `Could not access maxi-adan/zeclio-setup-claude` (Windows) | `GH_TOKEN` is not defined or is invalid | Check: `echo $env:GH_TOKEN`. If empty, repeat step 3.2 |
| `Could not access maxi-adan/zeclio-setup-claude` (Mac/Linux) | `GH_TOKEN` is not defined or is invalid | Check: `echo $GH_TOKEN`. If empty, repeat step 3.2 |
| `mwc.md not found` | `npm run build` was not run before `sync:docs` | Run `npm run build` in `maxi-libs/web-components/core/` first |
| Action doesn't trigger on merge | The PR doesn't touch files inside `templates/` | Check the Actions tab in the repo. The trigger is configured only for changes inside `templates/` |
| Nexus publish error | `NEXUS_TOKEN` expired or not configured | Verify the `NEXUS_TOKEN` secret is set in Settings → Secrets and variables → Actions in the repo |
| Docs don't update in the project after merge | The new version hasn't been downloaded locally yet | Run `npx zeclio-setup-claude` in the project. If you already ran it and it didn't change, verify the Action completed successfully |
| `sync:docs` opens a PR but doesn't update `maxi-setup.md` for the new doc | The new doc is missing frontmatter with `description:` | Add the frontmatter block to the top of the `.md` (see section 9) and run `sync:docs` again |
